## Two separate problems, and the second was the dangerous one

**No door.** Seating existed only as a founder CLI (`run.py:4137`). A customer
who wanted a second reviewer on their evidence had to email us and wait for an
SSH session. For a product whose buyer is an MLRO who must *evidence* review,
"your colleague cannot log in until we run a command" is not a missing nicety.

**The seat did nothing.** This is the one I would have shipped straight past.
Every user owns a backfilled org-of-one, and `_resolve_from_db` prefers the org
you OWN — so an `auditor` seat in the customer's org lost to the colleague's own
empty workspace. `assign_org_role` returned `{"ok": True}`, a row landed in
`org_members`, the CLI printed success, and the colleague signed in to nothing.
An HTTP button on top of that would have been a lie with a 200 status code.

The owned-org preference is not a bug — it is deliberate and correct for a solo
user, whose own data must stay reachable. Both cannot be true with a single
implicit org, so there is now an explicit one: `users.active_org_id`. NULL for
every existing row and every new signup, which makes the column **inert** until
someone is actually seated twice; the solo path is byte-for-byte the old one.

`assign_org_role` sets it only when the target has made no choice, so no owner
can yank a person out of the org they are currently working in.

## Security posture

Authorization is not re-implemented in the HTTP layer. Every mutation goes
through `app.rbac_runtime`, where `member.manage` is owner-only under the role
matrix and `app.rbac.can` confines an owner to their own org. The roster query
is bounded to `principal.org_id` and never to a caller-supplied one, so there is
no shape of request that reads another tenant's members.

A stale or tampered `active_org_id` grants nothing: `_resolve_from_db` only ranks
orgs the membership `WHERE` already matched, so a column pointed at a stranger's
org selects no row and falls through. Pinned by a test.

The two boundary tests were checked for vacuity by removing the `can()` guard —
both fail without it, and the file was restored byte-identical afterwards.

## What is NOT done

- **No email invite.** You can only seat someone who already registered; an
  unknown address returns 404 with `no_such_account` and the UI says "ask them to
  register first". Inviting by email needs deliverability the verification path
  only just got, and half an invite system is worse than none.
- **No org switcher in the UI.** `set_active_org` exists and is membership-gated,
  but nothing renders it — a person seated in two orgs stays where they are.
- **Not visually verified.** Settings is behind the auth wall and I do not enter
  credentials. The panel is covered by 6 jsdom render tests and a production
  build, not a screenshot.
