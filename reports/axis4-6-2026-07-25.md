# Axes 4 and 6 — customer path, test isolation

Branch `tenten`. Nothing deployed.

## Axis 6 — test isolation

### What was wrong

`tests/conftest.py` was 16 lines of `sys.path` setup. Measured with
`tools/measure_test_isolation.py` (committed): running
`tests/test_export_authz_limits.py` **alone** changes the working `regradar.db`.
For a product whose entire claim is evidence integrity, a suite that writes into
its own store is one stray `pytest` away from a corrupted artifact — and it makes
every "the database says X" observation during development untrustworthy.

### The fix

`app/db._connect()` reads `app.db.DB_PATH` at **call** time (`app/db.py:40`), so an
autouse fixture that repoints that module attribute covers every test without
import-time environment juggling. Tests that already redirect the DB themselves
still win — their function-scoped patch applies after the autouse one.

Proof it works, rather than an assertion that it should: a canary database was
written into a clean worktree, the previously-offending module was run, and the
file's SHA-256 was **identical** before and after.

### The one regression it caused, and why it is worth recording

The first version also did `os.makedirs(tmp_path / "data")`. That broke
`test_load_json_artifact_resolves_relative_paths_against_base_dir`, which calls
`.mkdir()` on that exact directory without `exist_ok`. Isolation must not reshape
the sandbox it hands over — the line is gone.

With it removed, the full suite in a **clean worktree** is green: pytest exit 0,
zero failures. That is the DoD's "suite green from a clean clone", measured rather
than assumed.

### Method note

The original plan was a per-module census — run all ~210 test modules in separate
processes and fingerprint the working artifacts around each. It was still running
after ~40 minutes, and it answers a question the DoD does not ask (per-module
blame). The DoD asks whether the SUITE touches working artifacts, which two
full-suite runs answer directly. The census was stopped and the tool kept, because
per-module attribution is the right instrument when hunting a specific offender.

### Honest limit

The fixture redirects the **database**. `BASE_DIR` is read at import time by
several store modules, so the env var it also sets only reaches code that resolves
it lazily and subprocesses a test spawns. A test that captured a store path at
import can still, in principle, write to the real tree. Nothing in the current
suite does — that is measured, not assumed — but the guarantee is narrower than
"no test can ever write anywhere".

## Axis 4 — the emailed verification link

### What was wrong

`app/api_auth.py:106` and `:242` built the verification URL as
`{base}/api/auth/verify-email?token=…` — the API endpoint. There is no
`/verify-email` route in `routeMap.js`, so the one link every single customer
clicks rendered raw JSON in their browser:
`{"ok": true, "verified": true, "message": "Email verified. Please sign in to continue."}`.

### The fix

The link now points at a page, which calls the same endpoint and shows a person
the result. The API is unchanged, and that matters: it deliberately does **not**
mint a session on this GET link, because a mailbox security scanner can pre-fetch
an emailed URL and a `Set-Cookie` would hand that party a live session for the
victim's account. The page therefore ends at "Sign in", never at a logged-in
state. The security property is preserved; only the presentation changed.

Seven tests cover it, including the two failure modes that matter: an expired link
is reported as a failure rather than dressed up as success, and an unreachable
server does not produce a success page. The single-use token is called exactly
once even across a re-render, since mail scanners already burn one fetch.

### Still open on this axis

- **Send failure is invisible.** Registration returns `ok: true` while the email is
  sent from a `daemon=True` thread whose result is discarded (`app/api_auth.py:107-112`).
  A customer whose mail never arrives sees a success screen.
- **Alert release still needs SSH.** `run.py alert-review` is the only path; there
  is no HTTP endpoint or UI to approve an alert for delivery.

Neither is fixed here, so axis 4 is **not** closed.
